# neon-information

Information and test data for [jclab-oss/neon](https://github.com/jclab-oss/neon).

## Testing

A Neon build, given as its published images, is tested by `.github/workflows/neon-test.yml`, all at the same time for each Postgres version and architecture:

- **compatibility** (`.github/actions/compatibility-test`): Neon's compatibility tests (`test_compatibility.py`) against the latest release of `testing/archive/upstream/`.
- **sqlancer**, **benchbase** (`.github/actions/workload-test`, `testing/workload/`): a workload ([SQLancer](https://github.com/sqlancer/sqlancer), [BenchBase](https://github.com/cmu-db/benchbase)'s TPC-C) on the main branches of two tenants, then on main and a branch of it at the same time. The scenario checks that the branch has main's data, that the branches and the tenants don't see each other's writes (an idle third tenant stays the same), that main's past doesn't change, and that all the data survives the pageserver and safekeepers being killed. If the build supports local branches (jclab-oss/neon's computes that keep their changes on their own disk), each tenant also gets one, tested the same way: the workload runs on it with the other branches, and the pageserver must never see its writes. SQLancer's findings are replayed on a vanilla Postgres: those it reproduces are only warnings. The report has BenchBase's results of each run (TPS, NewOrder/min, latencies, transactions by outcome).

It runs:

- on pull requests (`.github/workflows/pr.yml`), for the build of `testing/version.yaml`, with the results commented on the pull request;
- on request in an issue (`.github/workflows/issue.yml`), for any build of jclab-oss/neon, e.g. a pull request's: open an issue with the "Neon test" form, or comment `/neon-test` followed by the request's `key: value` lines (see `.github/scripts/neon-test-request.py`). Only users with write access to this repository can request tests. The results are commented on the issue.

The other parts:

- `testing/archive/<archive>/<release>/`: the compatibility data of a release.
  - `compatibility-snapshot-<X64|ARM64>-release-pg<v16|v17>.tar.zst`: `test_compatibility.py::test_create_snapshot`'s snapshots (Git LFS).
  - `info.yaml`: the images of the release's binaries.
  - `upstream/` holds upstream Neon's releases. Their data are generated by the `test-generator/upstream` branch of jclab-oss/neon, from the images upstream published. They are imported by the `Import compatibility snapshots` workflow, given that run's ID.
- `testing/tools/Dockerfile`: the image the workload tests run in (build-tools with Java, SQLancer and BenchBase), built by `neon-test.yml` when it changes.
- `.github/actions/setup-neon`: extracts a build's binaries from its images and runs Neon's Python tests with them, for the other actions. The actions expect this repository checked out at the workspace root.
